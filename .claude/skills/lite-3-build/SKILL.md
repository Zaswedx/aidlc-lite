# /lite-3-build — ③ 구현 (스토리 1개)

- 공통 규칙: `.claude/skills/lite/rules.md` 를 먼저 읽고 따름
- 원래 AI-DLC 의 Code Generation 을 압축한 단계 (TDD 3세션 → 로직만 테스트 먼저, 한 세션)
- 인자: 스토리 ID (`$ARGUMENTS`, 예 `US-01`). 없으면 state.md 의 첫 미완료 스토리를 제안하고 확인
- 입력: `requirements.md` (해당 스토리 · AC), `design.md`, `data-rules.md` (승인됨)
- 산출물: 코드 · 테스트 (프로젝트 기존 위치 · 컨벤션 따름)

## 절차

1. **기준선**: 전체 테스트 실행. `current-state.md` 기준선보다 실패가 늘었으면 구현 전에 보고하고 멈춤
2. **작업 계획** 출력 (승인 대기 없이 진행, 사람이 멈추면 중단)

   | 순서 | 작업 | 대상 파일 | 근거 (BR · AC · API) | 테스트 먼저? |
   | --- | --- | --- | --- | --- |

   - 테스트 먼저 = API · DB · 업무 규칙 · 입력 검증 / 구현 후 확인 = 순수 화면 배치 · 스타일

3. **로직 (테스트 먼저)** — 규칙 · AC 단위로 반복
   1. RED: 설계 문서의 값 그대로 실패하는 테스트 작성 → 실행
      - 실패 이유가 기대값 불일치 (AssertionError, 상태 코드 불일치) 인지 확인. ImportError · fixture 오류는 테스트를 고침
      - 테스트 첫 줄 주석에 규칙 ID: `# BR-01: 제목 100자 초과 → 400`
   2. GREEN: 테스트를 고치지 않고 최소 구현으로 통과
   3. 정리: 동작을 바꾸지 않고 중복 · 이름 정리 → 다시 실행
4. **스키마 변경**: `data-rules.md` 에 있는 것만, 기존 마이그레이션 방식으로. 테스트 DB 에서 먼저 확인
5. **화면**: 구현 후 개발 서버에서 해당 화면 확인 (Playwright · Chrome DevTools MCP 가 있으면 스크린샷, 없으면 확인 방법을 사람에게 안내)
   - design.md 의 상태 (로딩 · 빈 화면 · 오류) 와 NFR 체크리스트 항목 확인
6. **마무리**: 전체 테스트 + lint 실행 → 기준선 대비 새 실패 0 확인
7. state.md 스토리 체크 (모든 스토리 완료면 `③ 구현` 도 체크, Next = ④), audit 기록
8. 보고: 바꾼 파일 목록, 추가한 테스트 (규칙 ID ↔ 테스트 이름), 화면 확인 위치 1줄, 다음 스토리 또는 `/lite-4-verify` 안내

## 금지

- 설계에 없는 기능 · 화면 · 컬럼 추가 (필요하면 멈추고 ② 수정 제안)
- GREEN 단계에서 테스트 기대값 수정
- 기존 테스트 삭제 · skip, 운영 DB 에서 마이그레이션 실행
